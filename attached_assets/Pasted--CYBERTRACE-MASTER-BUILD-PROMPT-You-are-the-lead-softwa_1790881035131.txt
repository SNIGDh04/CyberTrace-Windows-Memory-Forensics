# CYBERTRACE — MASTER BUILD PROMPT

You are the lead software architect, Python developer, DFIR/memory-forensics engineer, backend engineer, frontend engineer, and QA engineer for this project.

Build a complete working MVP called:

**CyberTrace: Evidence-Driven Attack Reconstruction from Volatile Memory**

This is a defensive digital-forensics and memory-analysis platform.

The goal is NOT to build another simple Volatility dashboard.

The core research idea is:

**Volatile Memory → Forensic Evidence → Evidence Correlation → Timeline → Evidence Graph → Possible Attack Reconstruction → Investigator Verification**

# 2. CORE PROBLEM

Traditional memory-forensics workflows often require investigators to manually inspect outputs from multiple forensic plugins and mentally correlate them.

CyberTrace should automate the correlation process.

For example:

Volatility may independently reveal:

* explorer.exe
* powershell.exe
* suspicious.exe
* a DLL associated with suspicious.exe
* a network connection associated with suspicious.exe

CyberTrace should correlate these observations:

explorer.exe
↓
powershell.exe
↓
suspicious.exe
↓
suspicious.dll
↓
external network endpoint

The system must NOT automatically state:

"The machine was definitely compromised."

Instead it should produce:

"Possible Attack Sequence"

and show the evidence supporting every step.

# 6. VOLATILITY 3 INTEGRATION

Integrate real Volatility 3.

Initial plugins:

* windows.info
* windows.pslist
* windows.pstree
* windows.cmdline
* windows.netscan
* windows.dlllist
* windows.malfind

Do NOT attempt to integrate dozens of plugins initially.

Create a reusable Volatility runner.

It should:

1. Accept a memory-image path.
2. Validate that the file exists.
3. Execute selected Volatility plugins.
4. Capture stdout/stderr.
5. Handle plugin failures gracefully.
6. Preserve raw plugin output.
7. Convert usable results into structured data.
8. Record which plugin produced each artifact.
9. Store analysis status and errors.

The system should never silently discard failed plugin execution.

# 9. CORRELATION ENGINE

This is one of the most important components.

Implement deterministic correlation rules.

## Rule 1 — Parent/Child

If:

child.PPID == parent.PID

create:

PARENT_CHILD

Example:

powershell.exe
↓
suspicious.exe

Store:

* source evidence
* target evidence
* relationship type
* reason
* source plugin
* confidence

---

## Rule 2 — Process / Network

If:

network.pid == process.pid

create:

PROCESS_CONNECTS_TO

Example:

suspicious.exe
↓
10.x.x.x:443

---

## Rule 3 — Process / DLL

If:

dll.pid == process.pid

create:

PROCESS_LOADS_DLL

---

## Rule 4 — Process / Command

If:

cmdline.pid == process.pid

create:

PROCESS_EXECUTED_WITH_COMMAND

# 11. THREE-LEVEL EVIDENCE MODEL

CyberTrace must distinguish:

## OBSERVED

Directly present in forensic evidence.

Example:

"PID 4120 exists."

## CORRELATED

Relationship created by joining multiple observed artifacts.

Example:

"PID 4120 is associated with network connection EV-042."

## HYPOTHESIS

An investigator-facing interpretation.

Example:

"The observed process and network activity may represent a related execution and communication sequence."

Use these labels throughout the UI.
